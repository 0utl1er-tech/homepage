# 読みものは一か所に、証拠はサービスの中に置く

調査した会社はどこも、ブログ・解説・事例を**自社ドメインの短いフォルダ（`/blog/`、`/customers/` など）**に置き、記事の最後に関連サービスへの案内を1〜2個だけ付けていました。0UTL1ERの規模なら、**読みものは `/blog/` に一本化し、`/guide` と `/glossary` は今は分けない**のがよいと考えます。分割の手本として検討していたDatabricksは、2026年に用語集をブログの「what-is」記事へ統合し、旧URLをブログに転送しています（[Databricks](https://www.databricks.com/glossary)）。Google側にも変化がありました。2024年以降、中身の薄いページを大量に作ると、人が書いたかAIが書いたかに関係なく「量産コンテンツ」としてスパム扱いされます（[Google スパムポリシー](https://developers.google.com/search/docs/essentials/spam-policies)）。2026年1月以降は、自社を1位にした「おすすめN選」記事が大きく順位を落としたと観測されています（[SERoundtable](https://www.seroundtable.com/googleself-promotional-listicles-update-40873.html)）。「安いサービス探してみました」型の比較記事は書いてかまいません。ただし次の3点を守る必要があります。1つ目は冒頭で「当社のサービスも含む比較です」と書くこと。2つ目は他社の料金を公式サイトから確認日付きで引くこと。3つ目は自社をいつも1位にせず、「こういう人には他社が向く」と書くことです。法律の面では、自社サイトに自社名で載せる記事はステマ規制の対象外です（[消費者庁](https://www.caa.go.jp/policies/policy/representation/fair_labeling/stealth_marketing)）。一方で、比較広告ガイドラインの3条件（根拠がある、正確に引用する、公平に比べる）と、根拠のない「No.1」の禁止はそのままかかります（[比較広告ガイドライン](https://www.caa.go.jp/policies/policy/representation/fair_labeling/guideline/pdf/100121premiums_37.pdf)）。事例をサービスページの中に置く方針は、業界の多数派（独立した `/customers`）とは違います。それでも小さい会社には十分成り立つ選択です。足りない点は、ナビに出さない「全事例一覧」ページを1枚作れば補えます。

## 海外SaaSは「検索で来る人向けの本棚」をナビから外している

海外の大手の配置は、ほぼ共通していました。**ブログと導入事例はヘッダーのメニューに出し、用語集や解説ライブラリはフッターに置くか、トップページからリンクしない**という分け方です。Databricksのトップページには `/glossary` へのリンクが1本もありません。Ahrefsは用語集をトップからリンクせず、競合比較の `/vs/` ページはフッターにしか置いていません（[Databricks](https://www.databricks.com/)、[Ahrefs](https://ahrefs.com/)）。Cloudflareは解説集の `/learning/` さえフッターだけです（[Cloudflare](https://www.cloudflare.com/)）。用語集や解説は、Googleで調べた人が直接たどり着くためのページです。サイトの中を回遊して読むものとは扱われていません。

URLは「種類を表す短い言葉＋記事名」で、階層は浅くしています。Zapierは「おすすめCRM」のような比較記事まで含め、読みものをすべて `/blog/{記事名}/` に平らに置いています。カテゴリは一覧ページにしか出しません（[Zapier](https://zapier.com/blog/best-crm-app/)）。注目すべきは、**2025〜26年に「分けていたものをまとめ直す」動きが続いていること**です。Databricksは用語集をブログへ（`/glossary/acid-transactions` → `/blog/what-are-acid-transactions`）、Snowflakeは guides と trending を `/fundamentals/` へ、Vercelは `/guides` を `/kb` へ移しています（[Databricks](https://www.databricks.com/blog/what-are-acid-transactions)、[Snowflake](https://www.snowflake.com/en/fundamentals/)、[Vercel](https://vercel.com/kb)）。各社とも理由は公表していません。ただ、短い定義ページは後述のAI要約に答えを取られやすく、長くて中身のある記事に寄せる方向だと読めます。これは推測です。

役割分担は次の4つにまとまります。ブログは新しい話題と意見を扱い、「〇〇とは」型の解説も吸収しつつあります。解説ライブラリは、本のように章立てした長期保存版です。比較のうち「おすすめN選」はブログに、「自社 vs 競合」は営業用ページに置きます。導入事例は証拠として独立させます。解説ページの型もほぼ共通で、最初に1文の定義、次に目次、仕組み・種類・注意点・よくある質問と続き、最後に「当社でできること」の節と控えめなボタンが1〜2個付きます（[Stripe](https://stripe.com/resources/more/card-authorization-explained)、[Databricks](https://www.databricks.com/blog/what-are-acid-transactions)）。インフラ系の会社はボタンを最後に1〜2個置くだけでした。ボタンを本文中に何度も入れていたのは、無料登録で売るSEOツール会社（Semrush）だけです（[Semrush](https://www.semrush.com/blog/banner-ad-sizes/)）。

導入事例の置き方は、ユーザーの方針と最も違う点です。**調べた海外企業はすべて事例を `/customers/` などの独立した一か所にまとめ、業種・製品・規模で絞り込めるようにしていました。製品ページは、そこから事例を「タイル」として引用表示するだけです**（[Stripe](https://stripe.com/customers)、[HubSpot](https://www.hubspot.com/case-studies)）。日本でも freee や SmartHR は `/cases/` で業種・従業員規模・課題・都道府県から探せる形にしています（[freee](https://www.freee.co.jp/cases/)、[SmartHR](https://smarthr.jp/case/)）。ただし、こうした会社は事例が何百件もあるので、絞り込みが必要になります。事例が数件から数十件の小さな会社では事情が違います。MEO専業のパルティータは事例を各サービスページの中に置いているようで（[パルティータ](https://partita.co.jp/)）、Sreakeやクラスメソッドは「サービスページに数件＋全体一覧」の両方を持っています（[Sreake](https://sreake.com/)、[クラスメソッド](https://classmethod.jp/)）。

鮮度の見せ方では、記事のURLを変えずに中身を更新し、更新日を新しくしていく運用が主流でした。Zapierの比較記事は2014年公開のURLのまま、2026年6月に更新されてタイトルも「2026年版」になっています（[Zapier](https://zapier.com/blog/best-crm-app/)）。HubSpotは、月間閲覧の70%と問い合わせの92%が公開1か月以上前の記事から来ていたと公表しています。古い記事を手直ししたところ、閲覧は平均106%増えました（[HubSpot](https://blog.hubspot.com/marketing/historical-blog-seo-conversion-optimization)）。

## 日本では「選び方を示す」型と「自社1位ランキング」型に分かれている

日本の大手SaaSも、解説記事はメインドメインのフォルダ（freee `/kb/`、マネーフォワード `/words/` や `/accounting/basic/`、バクラク `/knowledge/`）に集めています（[freee](https://www.freee.co.jp/kb/kb-accounting/)、[マネーフォワード](https://biz.moneyforward.com/words/)）。freeeは旧来の別ドメインのメディア「経営ハッカー」の更新を2024年11月で事実上止め、`/kb/` を育てています（[経営ハッカー](https://keiei.freee.co.jp/)）。ヘッダーに「導入事例・お役立ち資料・セミナー」を並べ、ボタンを「資料ダウンロード・無料トライアル・お問い合わせ」の3つにするのが日本の定番です（[SmartHR](https://smarthr.jp/)、[バクラク](https://bakuraku.jp/)）。

比較記事の書き方には、日本ならではの特徴がありました。**freeeもマネーフォワードも競合の名前は出しますが、順位は付けません**。示すのは「選ぶときの基準」で、その基準の中に自社の強みを入れ込む書き方です。freeeは比較の基準として「連携できる銀行の数」を挙げ、そこに自社の3,200行以上を置いています（[freee](https://www.freee.co.jp/kb/kb-accounting/comparison-of-accounting-system/)）。マネーフォワードは競合6製品を名前で紹介しますが、比較表は「クラウド型かインストール型か」という型の比較にとどめています（[マネーフォワード](https://biz.moneyforward.com/accounting/basic/568/)）。バクラクは記事の本文に競合名を出さず、名前入りの比較は資料ダウンロードに回しています（[バクラク](https://bakuraku.jp/resources/how-to/resources-comparison-expense/)）。ただし「この記事は当社が書いています」という明示は、どの社にもありませんでした。有名なブランドなら、ロゴが書き手の表示を兼ねるからです。無名の小さな会社は、ロゴだけでは書き手が伝わりません。

0UTL1ERが実際に競う「MEO対策 代行 料金」や「SEO 会社 埼玉」の検索では、上位がほぼ全部、MEO・SEO業者自身の比較・相場記事でした（[gyro-n](https://www.gyro-n.com/seo/hack/meo_company/)、[rank-quest](https://rank-quest.jp/column/column/saitama-seo)）。書き方は対照的な2つに分かれます。StockSunの「MEO対策を格安で依頼できる代行業者ランキング」は、1位が自社サービス、2位が自社です。PR表記はなく、自社の料金欄は「要相談」でした（[StockSun](https://stock-sun.com/column/meo-cheap/)）。MEO TIMESは運営元と自社サービスを含むことを明かしています。そのうえで、25社の公式サイトを2026年8月10日に調べたと調査日と方法を書き、自社も同じ基準で並べています（[MEO TIMES](https://www.meo-times.com/meo/meo-agency/)）。この調査で分かったことがあります。**料金を公開していたのは25社中14社だけで、7社はMEOと関係ない実績を掲げ、実績に時点を書いていたのは4社、2年以内の実績を出していたのは1社だけ**でした（[MEO TIMES](https://www.meo-times.com/meo/meo-agency/)）。つまり、料金を数字で出し、日付入りのMEO実績を載せるだけで、この業界では上位数社に並べます。

久喜周辺の競争は弱めです。「ホームページ制作 久喜」で上位に出るのは、ブログも料金表示もない地元の制作会社か、市区町村名を差し替えたエリアページを100枚以上持つ域外の会社でした（[iorange](https://iorange.jp/)、[cantik](https://cantik.co.jp/kuki/)、[スタンダードラボ](https://www.standard-lab.com/area/saitama-kuki.html)）。企業向けの開発・インフラ側では、事情が逆になります。手本になるMSP（サーバー運用を請け負う会社）のハートビーツやSreakeは料金を出していません。代わりに自社ドメインの技術ブログで腕前を見せ、記事から関連サービス・事例・相談へとつないでいます（[ハートビーツ](https://heartbeats.jp/)、[Sreake](https://sreake.com/)）。Zennは多くの会社で採用広報の場として使われています。問い合わせを取る導線は自社ドメイン側にあります（[クラスメソッド](https://classmethod.jp/cases/flinters-zenn/)）。

## Googleは「量」と「自画自賛」を減点し、AI要約が解説記事のクリックを奪っている

Googleのスパムポリシー（2026年8月更新）は、「検索順位を操作する目的で、利用者の役に立たないページを大量に作ること」を量産コンテンツの不正利用と定義しています。生成AIでも人の手でも扱いは同じです（[Google スパムポリシー](https://developers.google.com/search/docs/essentials/spam-policies)）。生成AIのガイドも、AIで価値を足さずに大量のページを作れば違反になり得ると明記しています。公開前に人が事実確認することも求めています（[Google 生成AIコンテンツ](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)）。地域ページにも同じ考え方が当てはまります。「地域や都市ごとにページを作り、1つのページへ誘導する」ことは「誘導ページ」の例として挙げられています（[Google スパムポリシー](https://developers.google.com/search/docs/essentials/spam-policies)）。もう1つ大事なのは、**評価がサイト全体にかかる**点です。役に立たないページが多いサイトは他のページも評価されにくく、そうしたページを削ると残りが良くなることがある、とGoogle自身が書いています（[Google コアアップデート](https://developers.google.com/search/docs/appearance/core-updates)）。薄い用語集を何百ページも作ると、サービスページまで巻き添えにしかねません。2026年はスパム関連とコアの更新が少なくとも6回ありました（[Google Search Status Dashboard](https://status.search.google.com/products/rGHU1u87FJnkP6W2GwMi/history)）。

比較記事について、もっとも直接関係する観測があります。**2026年1月、自社を1位にするSaaS・B2Bの「おすすめ」記事が大きく順位を落としたと、Lily RayとGlenn Gabeが報告しています**。例として、「best seo agency」で自社を1位にしていた広告代理店が挙がりました（[SERoundtable](https://www.seroundtable.com/googleself-promotional-listicles-update-40873.html)）。Googleは公式には認めていないので、確定した事実ではありません。Rayは別の調査も行いました。「best ○○ software」100検索を調べたところ、AI要約（AI Overviews＝検索結果の上にGoogleが出す要約文）は自画自賛型の記事を出典に使いながら、**69%のケースで書いた会社自身を推薦から外していた**といいます（[ALM Corp](https://almcorp.com/news/self-promotional-listicles-ai-overviews-help-competitors-lily-ray-study/)）。Googleがレビュー記事に求めているのは、実際に使った証拠、他社との違いの説明、数字での比較、長所と短所の両方です（[Google 質の高いレビュー](https://developers.google.com/search/docs/specialty/ecommerce/write-high-quality-reviews)）。

AI要約がどの程度効いているかは、質問の種類で大きく違います。53ブランドを調べたSeer Interactiveの集計では、比較系の検索の95.4%にAI要約が出ていました。一方、「依頼したい」「買いたい」系の検索では5〜8%にとどまります。要約の出典に選ばれたページは、選ばれないページよりクリックが120%多くなりました（[Seer Interactive](https://www.seerinteractive.com/insights/aio-impact-on-google-ctr-2026-update)）。要約が出るとクリックする人は15%から8%へほぼ半減する、という調査もあります（[Pew ほかの集計](https://presenc.ai/research/ai-overviews-ctr-impact-2026)）。要約の出典の76%は、通常の検索で10位以内のページです（[Ahrefs](https://ahrefs.com/blog/search-rankings-ai-citations/)）。用語集はさらに不利です。304ページの用語集を持つサイトの実験では、平均順位が47位から18位に上がったのに、Googleでのクリック率は0.10%でした。AIの回答で出典に使われる回数は他のページの38倍あったので、用語集の効き目はAIに引用されることのほうに出たと言えます（[Otterly.ai](https://otterly.ai/blog/geo-experiment-seo-glossary-pages/)）。小さな会社にとって、用語集は集客の柱になりません。他の記事を支える脇役です。逆に、「久喜 MEO 代行」のような依頼する気のある検索は、AI要約に取られにくいままです。日本市場に限ったAI要約のデータは見つからなかったので、ここは海外の数字からの推定です。

鮮度について、Googleは日付の正直さを求めています。「最終更新日」を見える形で書き、ページの裏側の日付データ（構造化データ）と一致させるよう指示しています（[Google 日付](https://developers.google.com/search/docs/appearance/publication-dates)）。逆に「中身をほとんど変えずに日付だけ新しくする」ことは、評価を下げる兆候として明記されています（[Google 有用なコンテンツ](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)）。転載についても指針が変わりました。Googleは2023年5月から、転載先では「この記事を検索に出さない」設定（noindex）が最も確実だとしています（[SERoundtable](https://www.seroundtable.com/google-updates-canonicalization-help-documentation-35329.html)）。Zennにはその設定がなく、「元記事はこちら」と伝える設定（外部canonical）も出力されません（[Zenn記事](https://zenn.dev/zhener/articles/zenn-canonical-crosspost-seo)）。同じ文章を丸ごと転載すると、Zenn版のほうが上に出る危険があります。

## 自社サイトの比較記事はステマ規制の外だが、比較広告の3条件は外れない

ステマ規制（2023年10月施行）の対象は、「広告なのに広告であることを隠す表示」です。**事業者自身のウェブサイトや公式SNSでの表示は「事業者の表示であることが明らか」とされ、対象外**です（[消費者庁](https://www.caa.go.jp/policies/policy/representation/fair_labeling/stealth_marketing)、[契約ウォッチ](https://keiyaku-watch.jp/media/kisochishiki/stealthmarketing/)）。ただし、営業・販促の担当者が個人のSNSで自社サービスを推すと、事業者の表示とみなされ得ます。その場合は「広告」「PR」などの表記が必要です。表記は文章の最初など目に入る場所に置く必要があり、ハッシュタグに紛れ込ませたり小さな文字で書いたりするのは認められません（[消費者庁 Q&A](https://www.caa.go.jp/policies/policy/representation/fair_labeling/faq/stealth_marketing/)）。「お客様の声」をこちらに都合よく選んで載せた場合も、事業者の表示になります。実際にRIZAPは、Instagramの投稿を自社サイトに転載したことで措置命令を受けました（[aksk-marketing](https://aksk-marketing.jp/archive/1654/)）。noteやZennに会社のアカウントで出すなら問題は小さいと考えられます。社員の個人アカウントで出すなら、冒頭で明記するのが安全です。

比較そのものは景品表示法で禁止されていません。比較広告ガイドラインが示す条件は3つです。**①主張が客観的に実証されている、②数字や事実を正確に引用する、③比べ方が公平である**（[比較広告ガイドライン](https://www.caa.go.jp/policies/policy/representation/fair_labeling/guideline/pdf/100121premiums_37.pdf)）。実務に直結する定めも多くあります。競合が自分で公表し、信頼できると認められる数字（公式サイトの料金など）は、実証済みとして扱えます。調査した機関や時点は表示するのが適当で、比較項目を都合よく選んで独自に点数化すると問題になります。販売を終えた商品と現行品を比べることも禁止されています（つまり、競合が料金を改定したら追いかけて直す必要があります）。長所と表裏一体の短所を隠せば不当表示のおそれがあり、事実であっても相手の信用を落とすような中傷は避けるべきとされています（同ガイドライン）。

「No.1」表示はさらに危険です。消費者庁は2024年9月の報告書で、主観的な評価に基づく「顧客満足度No.1」などの表示には合理的な根拠が必要だと示しました。主要な競合を比較対象に含めること、偏りのない回答者を選ぶこと、公平な調査方法をとること、表示と結果を一致させることが条件です。報告書が出るまでに14社が措置命令を受けています（[池田・染谷法律事務所](https://www.ikedasomeya.com/insight/20724)）。広告主15社のうち14社は調査会社に丸投げしていましたが、責任は広告主にあるとされました（[Web担当者Forum](https://webtan.impress.co.jp/e/2024/12/06/48216)）。

不正競争防止法にも実例があります。札幌地裁の令和6年2月27日判決は、自社サイトの根拠のない「ランキング1位」表示を、品質を誤って伝える表示（2条1項20号）と認定しました。価格や条件についての虚偽の比較も不法行為とし、「広告代行業者に任せた」という言い分は通りませんでした（[GVA五常法律事務所](https://www.gojo-partners.com/column-ps/6489/)）。0UTL1ERには二重の意味があります。自社の記事で注意が必要なのはもちろんです。加えて、MEO・SEO代行として顧客向けに比較記事を作るなら、顧客とともに自社も責任を問われ得ます。競合のロゴやURLに競合名を使うことの扱いは、日本の一次資料を確認できていません。ロゴは使わず、名前を文中で記述的に使う程度にとどめるのが安全です。

## 0UTL1ERへの提案：URL・ナビ・比較記事の型・作る順番

### URLの地図

ユーザーが決めた「サービス▾ / ブログ（読みもの） / 会社情報 / [お問い合わせ]」の形は、調査結果と矛盾しません。むしろ、日本のSaaSのように資料・セミナーを並べず、読みものを1つの入口にまとめている点は、1〜3人の会社に合っています。以下が推奨するURLの地図です。

| URL | 中身 | ナビでの位置 |
|---|---|---|
| `/` | 2つの入口（「お店・地域の事業者さま」「開発・クラウドをお探しの企業さま」） | — |
| `/services/` | サービス一覧 | ヘッダー「サービス▾」 |
| `/services/{service}/` | サービスLP（料金・流れ・FAQ・事例数件・相談ボタン） | ヘッダー「サービス▾」の中 |
| `/services/{service}/cases/{slug}` | 個別事例（正本はここ） | サービスページ内から |
| `/cases/` | 全事例の一覧（サービス・業種・地域で絞り込み。リンク先は上の正本） | ヘッダーには出さず、フッターと各事例ページから |
| `/blog/` | 読みもの一覧 | ヘッダー「ブログ（読みもの）」 |
| `/blog/{slug}` | すべての記事（解説・選び方・比較・相場・技術・お知らせ） | — |
| `/blog/category/{cat}` | カテゴリ一覧（例: `mise`＝お店の集客、`tech`＝開発・インフラ、`news`） | ブログ一覧内のタブ |
| `/company/`、`/contact/` | 会社情報、問い合わせ | ヘッダー |
| `/kuki/`（任意、1枚だけ） | 久喜の本物の地域ページ（本社所在地、久喜での実例、訪問対応範囲） | フッター |

**`/guide` と `/glossary` は今は作らない**ことを勧めます。理由は3つあります。1つ目に、分割の手本だったDatabricks自身が用語集をブログに統合しています。2つ目に、用語集はGoogleからのクリックをほとんど生みません。3つ目に、短いページを量産すると、サイト全体の評価を下げる側に働きます。「〇〇とは」型の解説記事は、Databricksと同じように `/blog/what-is-xxx` のような記事名でブログに入れれば足ります。将来、MEOの解説記事が章立てした「本」の形にまとまったら、そのとき `/guide/meo/` を作り、元の記事を301転送（自動で新しいURLへ案内する設定）すれば済みます。記事名は英語の短い固定スラッグにしてください。URLに日付を入れないことと、フォルダを深くしないことも、後の整理を楽にします。

事例をサービスページの中に置く方針は、海外の大手とは違います。ただ、事例が数十件までの会社なら、このほうが「このサービスで何が起きたか」を1ページで読ませられるので合理的です。失うのは「全部の事例を業種や地域で探せる」機能だけです。そこはナビに出さない `/cases/` 一覧で補い、各事例のURLはサービスの中の1つだけにしてください（同じ事例を2か所に置かない）。開発とMEOの両方に関わった事例は、主になったサービスの下に置き、もう一方のサービスページからはタイル表示でリンクします。事例には日本の型を使います。見出しに数字（例「マップ表示回数が3か月で2.1倍」）、冒頭に「課題／やったこと／結果」の要約、業種と市町村、時点を入れてください（[SmartHR 事例](https://smarthr.jp/case/konoike-unyu/)）。

### 比較・選び方ページの型

「安いMEO代行を探してみました」型の記事は `/blog/` に置き、該当サービスページの「ほかの会社とくらべる」欄からリンクします。海外のような競合名入りの `/vs/` ページは、0UTL1ERには不要です。指名で比較される規模ではないうえ、自画自賛型の比較ページはいま最も順位を落としやすい形だからです。記事は次の順に組みます。

| 順 | 中身 | 根拠 |
|---|---|---|
| 1 | タイトル（年号は中身を更新したときだけ変える） | Google 日付ガイド |
| 2 | **冒頭の開示文**（下記） | ステマ規制・Googleレビュー指針 |
| 3 | 公開日・最終更新日・書いた人（実名と役割） | Google 日付ガイド |
| 4 | 結論の早見表（「〇〇な人にはA社、△△な人には当社」） | Zapier型、AI要約に引用されやすい |
| 5 | 調べ方（何社を、いつ、どこから、何の基準で） | 比較広告ガイドライン4.(2)、MEO TIMES型 |
| 6 | 比較表（料金は同等プラン同士、各社公式URLと確認日つき） | ガイドライン3.(2)・5.(2) |
| 7 | 各社の紹介（長所と短所の両方。他社が勝つ点も書く） | ガイドライン5.(3)・6、Googleレビュー指針 |
| 8 | 当社について（料金を数字で。安さの理由と、その代わりできないこと） | ガイドライン5.(3) |
| 9 | 選び方のチェックポイント（自社に有利な基準だけにしない） | freee型 |
| 10 | 相談ボタン1つ＋関連サービスページへのリンク | インフラ系各社の控えめ型 |
| 11 | 変更履歴（「2026-11: B社の料金改定を反映」） | Google 有用なコンテンツ |

冒頭の開示文の例です。

> この記事は、埼玉県久喜市の 0UTL1ER株式会社が書いています。比べている会社の中に、当社の「MEO運用代行」も入っています。他社の料金と内容は、2026年〇月〇日に各社の公式サイトで確かめたものです（当社調べ）。その後に変わっていることがあるので、申し込む前に各社の公式サイトでもご確認ください。当社がいちばん合う、とは限りません。記事の最後に「当社が向かない方」も書いています。

比較表の下には「料金はすべて税込・1店舗あたりの月額。〇年〇月〇日時点、各社公式サイトの公開情報より当社調べ」と注記を付けます。「No.1」「最安」「業界最高」は使いません。もし「最安」と書くなら、比べた会社の数・日付・条件を同じ場所に書き、条件を満たす本当の事実に限ります。自分で付けた点数による総合順位も付けないでください。代わりに「用途別のおすすめ」にします。

### ボタンと導線

ボタンは客層ごとに分けます。店舗向けの記事とサービスページでは、料金を数字で出したうえで、「無料で相談する」（またはGoogleビジネスプロフィールの無料診断）を1種類だけ置きます。料金を出している会社が25社中14社しかない業界なので、それだけで目立てます（[MEO TIMES](https://www.meo-times.com/meo/meo-agency/)）。企業向けの技術記事では、記事末尾に関連サービスへの固定の案内を置き、ボタンは「技術相談」1種類にします（[Sreake](https://sreake.com/)）。開発・クラウドは見積もり型なので、料金は「目安」か「相談」で構いません。記事の途中にボタンを何度も挟むのはやめましょう。最後に1つ、多くても冒頭と最後の2つにとどめます。解説記事は、一般的な説明を先に書き、最後に「0UTL1ERでできること」の節を1つ置いてサービスページへつなぎます。トップページの2つの入口から、それぞれのブログカテゴリ（`mise`／`tech`）へもリンクします。そうすれば、店舗オーナーが技術記事に迷い込むことは減ります。

### 鮮度の管理とZenn・noteへの転載

日付は公開日と最終更新日を両方表示し、構造化データの日付と一致させます。最終更新日は、中身を本当に直したときだけ動かしてください。比較・相場記事は四半期に1回、他社の公式料金を確認し直します。競合の改定を見つけたらその時点で直します。旧料金のまま比べると、ガイドラインが禁じる「販売中止品との比較」に近い状態になるからです。解説記事は年1回の見直しで十分です。表示も問い合わせもなく、リンクもされていない記事は、関連記事に統合して301転送するか、削除します。

転載は、自社ブログに先に出し、Googleに登録されたことを確かめてから行います。Zenn（技術者向け）とnote（店舗オーナー向け）には全文をそのまま載せず、読者に合わせて書き直した要約版にします。冒頭には「元の記事は0UTL1ERのブログにあります」とリンクを置きます。社員の個人アカウントで出すときは、本文の最初に「筆者は0UTL1ERの社員で、この記事は当社のサービスを含みます（PR）」と書きます。

### 1〜3人での作る順番

| 順 | 作るもの | 目安 |
|---|---|---|
| 1 | サービスページ（料金・流れ・FAQ）とGoogleビジネスプロフィールの整備 | 最初の1か月 |
| 2 | 各サービスに事例を1〜3件（数字・時点・業種・市町村入り）と、ナビに出さない `/cases/` | 並行して |
| 3 | 店舗向けの「MEO代行の料金相場と、うちの料金」記事を1本（上の比較の型） | 2か月目 |
| 4 | 自社の手順やデータに基づく深い解説を3〜5本（MEO・HP制作・プライベートクラウド運用） | 2〜4か月目 |
| 5 | 技術ブログ（運用の実録）を月1〜2本。Zennへ書き直し版を転載 | 継続 |
| 6 | 久喜の地域ページを1枚（本物の地元事例が出てから） | 事例がそろってから |
| 7 | 用語の解説は、必要になった言葉だけ記事の中か1枚のまとめページで | 後回し |

### やらないこと

| やらないこと | 理由 |
|---|---|
| 市町村名を差し替えた地域ページの量産 | Googleの「誘導ページ」の典型例 |
| 1語1ページの薄い用語集を何十・何百と作る | クリックはほぼゼロ、サイト全体の評価を下げ得る |
| AIで下書きした記事を人の確認なしに公開する | Googleが公開前の人による確認を求めている |
| 自社を常に1位にするランキング記事 | 2026年に順位下落が観測、札幌地裁判決のリスク |
| 根拠のない「No.1」「満足度〇%」「最安」 | 景品表示法の措置命令が相次いでいる |
| 競合の旧料金や違うグレードとの比較、悪口 | 比較広告ガイドライン5.(2)・6 |
| 中身を変えずに日付やタイトルの年号だけ更新 | Googleが評価を下げる兆候として明記 |
| 自社を隠した「中立風」の比較サイトを別に作る | ステマ規制と不正競争防止法の典型的なリスク |
| ZennやnoteへのPR表記なしの全文転載 | 転載先が上位に出る、個人アカウントはPR表記が要る |
| MEOと関係ない実績（会社全体の取引社数など）を掲げる | 業界で信用を落としている典型 |
| 自社の評価に星やレビューの構造化データを付ける | Googleのスパム的な構造化データとして扱われる |

## Conclusion

この調査で分かったのは、「どこに置くか」より「何を正直に書くか」で差がつく時代になったことです。大手が分けた本棚をまとめ直しているのは、ページの数で稼ぐやり方が、Googleの量産判定とAI要約の両方から締め出されつつあるからです。小さな会社にとってはむしろ追い風で、業界の半分近くが料金を出さず、実績に日付を書いていない分野です。料金を数字で書くこと、日付入りの地元の事例を載せること、自社の限界も書いた比較記事を出すことは、法律上の安全策であると同時に、他社との違いそのものになります。

残る不確かさは2つです。自画自賛型の比較記事が下落した件はGoogleが認めておらず、日本の検索でのAI要約の影響を示すデータもまだありません。ですから、比較記事は1本を丁寧に作り、半年ほど検索での表示回数と問い合わせを見てから2本目に進むのが確実です。事例を各サービスの中に置く設計は、事例が50件を超えたあたりで見直すとよいでしょう。そのときは `/cases/` を正本に移して301転送するだけで、海外の多数派の構造に切り替えられます。
