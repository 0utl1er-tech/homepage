# ブログの構造化 — 自社ブログを正本に、Zenn・note へ配る

前提: [01-information-architecture.md](01-information-architecture.md) の「見込み客は2種類（店舗・地域ビジネス / 企業のIT担当）」という分け方を、ブログにもそのまま使う。

---

## 1. 3つの場所の役割

| | 自社ブログ（0utl1er.tech/blog） | Zenn | note |
|---|---|---|---|
| 役割 | **正本**。検索流入をためる資産。問い合わせにつなげる場所 | 技術者への露出。技術力の証明。採用 | 経営者・店舗オーナーへの露出。人柄・考え方を伝える |
| 読者 | A・B 両方 | B（開発・インフラ）とエンジニア採用候補 | A（集客支援の見込み客） |
| 書く内容 | すべて | 技術記事だけ | 集客・経営・会社の考え方 |
| 置く版 | 完全版 | 技術者向けに組み直した版 | 読み物として組み直した版 |
| ゴール | 問い合わせ、サービスページへの移動 | 自社ブログ・会社ページへのリンク、フォロー | 自社ブログ・集客支援ページへのリンク、フォロー |

**流れは常に「外 → 自社」**。Zenn と note は人を集める場所、自社ブログは受け止めて問い合わせにつなげる場所。

---

## 2. 重複コンテンツの扱い（いちばん大事なルール）

### 事実
- **Zenn は外部 canonical を設定できない。** front matter に書いても公開 HTML は Zenn 自身を指したまま（[調査記事](https://zenn.dev/zhener/articles/zenn-canonical-crosspost-seo)）。
- **note も一般アカウントでは記事ごとに外部 canonical を指定できない**（note 自身を正規 URL にする自動設定のみ）。
- Google は、他サイトへ配信した記事は canonical より「配信先で noindex にする」か「内容を変える」ことを勧めている。Zenn と note では noindex にできない。
- 同じ全文が3か所にあると、Google は**ドメインの強い Zenn / note の方を正本と見なしやすい**。自社ブログは評価を取られる。

### ルール
1. **全文をそのまま転載しない。** 外部には「その場所の読者向けに組み直した版」を置く（§6 で具体化）。
2. **自社ブログで先に公開する。** Search Console でインデックスを確認してから（目安: 3〜7日後）外部に出す。
3. **外部版の冒頭か末尾に必ず原典リンク**を入れる。「完全版・図表つきは自社ブログで」のように、移る理由も添える。
4. **自社ブログ側だけに置くもの**を毎回つくる: 図表、チェックリスト、事例の数字、関連サービスへの案内、FAQ。外部版との差になり、自社に来る理由にもなる。

## 3. 自社ブログの読者とカテゴリ

カテゴリは**少なく、固定**にする。読者の種類で分けて、サービスページと1対1で対応させる。細かい話題はタグで扱う。

| カテゴリ（表示名） | slug | 読者 | つなぐサービスページ | 配信先 |
|---|---|---|---|---|
| 集客・MEO | `local-marketing` | A | 集客支援 | note |
| Web・SEO | `seo` | A（一部 B） | 集客支援 | note |
| 開発 | `development` | B・採用 | 受託開発 | Zenn |
| インフラ・クラウド | `infrastructure` | B・採用 | プライベートクラウド | Zenn |
| 会社・考え方 | `company` | 全員 | 会社情報 / 採用 | note |

- **お知らせはブログに混ぜない。** 「料金改定」「年末年始休業」は検索資産にならず、ブログ一覧を薄く見せる。お知らせは別の一覧（`/news`）に分ける
- 事例は専用ページ（`/cases`）に置き、ブログからリンクする。事例の数字は営業資料でもあるので、ブログに埋もれさせない

### タグ
- 自由に付けてよいが、**1記事3〜5個まで**（Zenn の topics 上限5に合わせる）
- 表記を固定する: `kubernetes`（`k8s` は使わない）、`google-business-profile`（`gbp` は使わない）など。表記の一覧を別ファイルで管理する
- 記事が3本未満のタグのページは noindex にする（中身の薄い一覧ページを検索に出さない）

## 4. URL とページの構成

```
/blog                         … ブログのトップ（新着＋カテゴリごとの人気記事）
/blog/{slug}                  … 記事（カテゴリを URL に入れない）
/blog/category/{category}     … カテゴリ一覧（説明文つき。これ自体が検索の受け皿になる）
/blog/tag/{tag}               … タグ一覧（3本未満は noindex）
/blog/author/{member-slug}    … 書き手ごとの一覧 → /members/{slug} と統合してもよい
/blog/feed.xml                … RSS
/news                         … お知らせ（ブログとは別）
/cases                        … 事例
```

- **カテゴリを URL に入れない**: 後からカテゴリを変えても URL が壊れない
- slug は英小文字・数字・ハイフンで、内容を表す語にする（例: `gbp-review-reply-templates`）。Zenn の slug 規則（12〜50文字、a-z0-9 と - _）にも合わせておくと、Zenn 版で同じ slug を使える
- 日付を URL に入れない（古く見える、更新しにくい）

## 5. 記事の型

書く前に型を選ぶ。型ごとに必須の要素を決めておくと、AI に下書きを書かせても「スカスカ」になりにくい。

| 型 | 目的 | 必須要素 | 例 |
|---|---|---|---|
| **事例** | 実績の証明 | 業種・規模、課題、やったこと、期間、結果の数字、お客様の一言（許可済み） | 「久喜の美容室、3か月でルート検索が2.4倍」 |
| **ハウツー** | 検索流入 | 誰の何の悩みか、手順（画面写真つき）、よくある失敗、無料でできる範囲と頼むべき範囲 | 「Googleの口コミに返信する手順と例文」 |
| **解説** | 判断材料を渡す | 結論を最初に、比較表、選び方、自社の立場の明示 | 「MEO代行の料金相場と、頼む前に確認すること」 |
| **技術記録** | 技術力の証明（Zenn 向け） | 環境とバージョン、起きたこと、原因、直し方、再発防止 | 「Cilium の LB マップに古い宛先が残って DNS が落ちた話」 |
| **考え方** | 人柄・信用 | 代表の実体験、判断の理由、具体的な場面 | 「社名を 0UTL1ER にした理由」 |

### 中身を濃くするための決まり
- **一次情報を必ず1つ入れる**: 自社で起きたこと、自社で測った数字、実際の画面、実際に受けた質問。どこにでも書いてあることだけの記事は出さない
- Google は「大量に生成された中身の薄いページ」をスパムとして扱う。AI に書かせるのは構成と下書きまでにして、一次情報と結論は人が入れる
- 技術記録の材料はすでにある: kuki-dc で起きた障害（Cilium の古い宛先、RGW の Host 厳格化、ストレージ満杯の連鎖など）は、そのまま Zenn で読まれる種類の記事になる。顧客名や内部の IP は伏せる

## 6. 正本のデータ構造（front matter）

正本は1つのファイル（または CMS の1レコード）にまとめ、そこから自社版・Zenn 版・note 版を作る。

```yaml
---
# --- 自社ブログ（正本） ---
slug: gbp-review-reply-templates
title: Googleの口コミに返信する手順と、そのまま使える例文12個
description: 120字前後。検索結果に出る説明文
category: local-marketing          # §3 の5つから1つ
tags: [google-business-profile, review, meo]
type: howto                        # case / howto / guide / tech / essay
author: kuroha-jo                  # /members/{slug} と同じ
published_at: 2026-10-20
updated_at: 2026-10-20             # 内容を直したら更新。記事に「更新日」として表示
cover: ./cover.png
related_service: /services/local-marketing   # 記事末尾の案内先
cta: free-audit                    # 末尾に出す問い合わせの種類
status: draft                      # draft / review / published

# --- 配信先（無ければ配信しない） ---
syndication:
  zenn:
    enabled: false
    slug: gbp-review-reply-templates
    title: （Zenn 用の題名。技術者向けに）
    emoji: "📝"
    type: tech                     # tech / idea
    topics: [googlemaps, api]      # 最大5。Zenn に実在する topic 名を使う
    published_at: 2026-10-27       # 自社公開の数日後
    body: ./zenn.md                # Zenn 用に組み直した本文
  note:
    enabled: true
    title: （note 用の題名。読み物として）
    published_at: 2026-10-27
    body: ./note.md
    url:                           # 公開後に記入（自社側から相互リンクするため）
---
```

### 置き場所の案
```
content/blog/
  gbp-review-reply-templates/
    index.md        … 正本（完全版）
    zenn.md         … Zenn 版
    note.md         … note 版
    cover.png
    images/
```

### 正本をどこに置くか
| 案 | 長所 | 短所 |
|---|---|---|
| **Git（Forgejo）の Markdown**（推奨） | Zenn の GitHub 連携と同じ形式で、Zenn 版をそのまま同期できる。差分と履歴が残る。Claude で下書き・校正しやすい | 社外の人やエンジニアでない人には書きにくい |
| Strapi（既存の CMS） | 管理画面で書ける。すでに動いている | Zenn・note 版を作る仕組みを別に作る必要がある。履歴が追いにくい |

推奨は Git。お知らせ（`/news`）は今の Strapi に残してもよい。

### 配信の仕組み
- **Zenn**: Zenn 用のリポジトリ（GitHub 連携が必要）の `articles/{slug}.md` に `zenn.md` を書き出す。front matter は Zenn が認める項目（title, emoji, type, topics, published, published_at）だけにする。手作業でも小さなスクリプトでもよい
- **note**: API が無いので手で貼る。貼る前に Markdown から note の書式に変換したものを用意しておく。公開後に URL を正本へ記入する
- 会社として Zenn に出すなら、個人アカウントか Zenn の「Publication」（組織名義でまとめる機能）かを決める

## 7. 外部版の作り方

| | 自社ブログ（完全版） | Zenn 版 | note 版 |
|---|---|---|---|
| 題名 | 検索語を入れる | 技術的な中身が分かる題名 | 読み物として気になる題名 |
| 冒頭 | 結論と、この記事で分かること | 前提環境と結論 | 体験談・場面から入る |
| 本文 | 全部 | 技術の核心（手順・設定・原因）。営業的な部分は削る | 考え方・気づき中心。手順の細部は削る |
| 図表・チェックリスト | 全部 | 必要なものだけ | 1〜2枚 |
| 事例の数字・料金 | 載せる | 載せない | 一部だけ |
| 末尾 | サービス案内と問い合わせ | 原典リンク・会社紹介1行 | 原典リンク・集客支援ページへのリンク |
| 分量の目安 | 100% | 60〜80%（組み直し） | 40〜70%（組み直し） |

- **Zenn は宣伝目的の記事を禁止している。** 会社の宣伝は末尾の1〜2行にとどめる。技術の中身で読ませる
- note は人に付くので、代表の名前と顔で書く方が読まれる
- 全部の記事を配る必要はない。目安: 技術記録はほぼ全部 Zenn へ、考え方と集客の話は選んで note へ、事例と料金の話は自社だけ

## 8. 自社ブログの記事ページに必要なもの

| 要素 | 理由 |
|---|---|
| 書き手の名前・写真・肩書と、メンバーページへのリンク | 誰が書いたかは Google の評価（経験・専門性）にも読者の信用にも効く |
| 公開日と更新日 | 情報の新しさを示す |
| 目次 | 長い記事の離脱を防ぐ |
| パンくず（ホーム › ブログ › カテゴリ › 記事） | 迷子防止と検索結果の表示 |
| 関連記事（同じカテゴリ・タグ） | 回遊 |
| **カテゴリに応じた末尾の案内** | 集客の記事なら「無料診断」、インフラの記事なら「クラウドの相談」。全記事同じ案内にしない |
| 外部版へのリンク（あれば） | 「Zenn でも公開しています」。フォロワーを増やす導線 |
| 構造化データ: BlogPosting, BreadcrumbList, Person（著者） | 検索結果の表示 |
| OGP 画像（記事ごと） | SNS・note・Zenn で共有されたときの見え方 |
| サイトマップへの自動追加と RSS | インデックスの速さ |

### サイト全体とのつながり
- **サービスページ → 関連記事**: 各サービスページの下部に、対応カテゴリの記事を3本出す
- **記事 → サービスページ**: 本文中に自然な形で1回、末尾の案内で1回
- **カテゴリページはその分野の入口として作る**: 一覧だけでなく、説明文と「まず読む3本」を置く
- 同じ話題の記事が増えたら、まとめ記事（その分野を網羅する1本）を作り、個別記事と相互にリンクする

**トップページ**: 01 §5 の「8. お知らせ」を「ブログ新着」に変える。入口の振り分け（2枚のカード）ごとに、そのカテゴリの新着を出してもよい

## 10. 効果の測り方

| 何を | どこで | 見る数字 |
|---|---|---|
| 検索からの流入 | Search Console | 記事ごとの表示回数・クリック数・検索語 |
| 外部からの送客 | GA4 | Zenn・note のリンクに `?utm_source=zenn&utm_medium=syndication` を付けて計測 |
| 問い合わせへのつながり | GA4 | 記事を読んだあとに問い合わせフォームを送信した数（カテゴリ別） |
| 外部での反応 | Zenn・note の管理画面 | いいね・スキ、フォロワー数 |

月1回、記事ごとに「検索で何位か / 何人来たか / 問い合わせにつながったか」を見て、伸びている話題を書き足す。半年以上動きが無い記事は、書き直すか統合する。

## 11. 決めてほしいこと

1. **正本の置き場所**: Git の Markdown（推奨） / Strapi
2. **Zenn の名義**: 代表の個人アカウント / 会社の Publication
3. **note の名義**: 代表個人 / 会社アカウント
4. **書く頻度**: 月に何本書けるか（目安: 始めの3か月は週1本。少なくても続く本数で決める）
5. **書き手**: 代表だけか、メンバーも書くか（書くなら全員分のメンバーページが必要）
6. **最初に力を入れるカテゴリ**: 集客・MEO（問い合わせに近い） / インフラ（材料がすでに多い）
