# 情報の構造化 — 第三者から見て、あるべき情報

目的: メニューバーとトップページの構造を決める。
考え方: 「自社が言いたいこと」から始めない。**誰が来て、何を確かめて、何を決めて帰るのか**から逆算する。
凡例: ✅ 現行HPにある / △ あるが薄い・裏付け無し / ✕ 無い

---

## 1. 誰がHPを見に来るか

会社のHPを開く人は、ほぼ全員が何かを**確かめに**来ている。広告やSNSで興味を持ったあと、「この会社は本物か、頼んで大丈夫か」を判断するために開く。

| # | 訪問者 | どこから来るか | 決めたいこと |
|---|---|---|---|
| A | **集客支援の見込み客**（地域の店舗・中小企業の経営者） | 営業メール・DM・紹介・「MEO 代行」検索 | 任せていいか、いくらかかるか |
| B | **開発・クラウドの見込み客**（企業の情シス・事業責任者） | 紹介・技術記事・比較検討 | 発注先の候補に入れるか |
| C | **既存の顧客** | ブックマーク・請求書・メール署名 | 連絡先、お知らせ、規約の確認 |
| D | **与信・取引の確認をする人**（取引先の経理、金融機関、派遣先、自治体） | 社名検索 | 実在する会社か、契約して問題ないか |
| E | **採用候補・協力エンジニア** | 求人媒体・SNS | 働く先として信用できるか、何をする会社か |
| F | **検索エンジン・AI** | 自動巡回 | 何の会社で、どこにあり、何を扱っているか |

**A と B は同じ会社の客なのに、知りたいことも言葉の通じ方もまったく違う。** A に「Kubernetes」「CNCF」は通じないし、B に「お店の検索順位が上がります」は刺さらない。ここがメニュー設計でいちばん大事な分岐になる（§4で扱う）。

## 2. 訪問者ごとの「確かめたいこと」と必要な情報

### A. 集客支援（MEO / SEO）の見込み客

| 確かめたいこと | 必要な情報 | 現状 |
|---|---|---|
| 何をしてくれるのか | 施策の中身（GBP の整備、投稿代行、口コミ返信、写真、サイト改善など）を具体的な作業で | ✕ |
| うちの業種でも効くのか | 対応業種、業種別の実績 | ✕ |
| 本当に効果があるのか | 事例（開始前→〇か月後の表示回数・電話数・ルート検索数など）、お客様の声 | ✕ |
| いくらかかるのか | 料金プラン、初期費用、最低契約期間、解約条件 | ✕ |
| 何をどれくらい報告してくれるのか | レポートの頻度と見本 | ✕ |
| 怪しい業者ではないか | 会社情報、代表の顔と名前、所在地、電話番号 | △ |
| 始めるまでの流れ | 相談→診断→契約→開始の手順と期間 | ✕ |

注意: 「1位を保証」「必ず上がる」は Google 自身が SEO/MEO 業者の危険信号として挙げている表現。保証ではなく、事例の数字で語る方が信用される。「No.1」表記や「お客様の声」は景品表示法・ステマ規制の対象になるので、根拠と本人の同意を残しておく。

| 技術力は確かか | 技術スタック、代表・メンバーの経歴、技術記事、公開リポジトリ | △（スタック名のみ） |
| どんな体制で動くのか | 人数、担当の割り振り、AI をどう使っているか | △（言葉だけ） |

## 3. 情報の全体像（中身で分けたツリー）

訪問者ごとの表を重ねると、必要な情報は次の8つに分かれる。メニューはこの分け方を元に作る。

```
0UTL1ER
├─ 1. 何をしている会社か ............ 一言の説明、事業の一覧と、誰向けか
├─ 2. 事業ごとの詳細
│   ├─ 集客支援（MEO / SEO / サイト制作）
│   │   └─ 施策内容・料金・流れ・事例・FAQ
│   ├─ 受託開発
│   │   └─ 対応領域・進め方・契約形態・実績
│   ├─ エンジニア派遣・育成 ※実施していれば
│   │   └─ 対象・条件・法定の情報公開
│   └─ マネージドプライベートクラウド
│       └─ 仕様・料金・SLA・データの所在・セキュリティ
├─ 3. 実績・事例 ...................... 事業をまたいで一覧（業種・事業で絞り込み）
├─ 4. 料金と進め方 .................... 事業ごとのページの中に置くのが基本
├─ 5. 会社の信用情報
│   ├─ 会社概要（§2-D の表）
│   ├─ 代表メッセージ・社名の由来
│   ├─ メンバー
│   └─ 拠点・アクセス（地図）
├─ 6. 発信 ............................ お知らせ / 技術記事・コラム
├─ 7. 採用 ............................ 募集要項、働き方
├─ 8. 規約・法定表示 .................. プライバシーポリシー / 情報セキュリティ方針
│                                       / 特商法表記 / 派遣の情報公開 / 利用規約・SLA
└─ 問い合わせ ......................... 全ページから1クリック
```

## 4. メニューバーの構成案

### 決めるべき分岐: 2種類の客を同じ入口で迎えるか

| 案 | 内容 | 向いている場合 |
|---|---|---|
| **① 1サイト・事業別メニュー** | 「サービス」の下に事業を並べる | 事業間で客が重なる。または会社の総合力を見せたい |
| **② 1サイト・入口を客で分ける** | トップで「店舗・地域ビジネスの方」「企業のIT担当の方」に分ける | 客層がはっきり2つに分かれている（**今の0UTL1ERに近い**） |
| ③ 別サイト | 集客支援を別ブランド・別ドメインにする | 集客支援の客に技術色を見せたくない。営業の主戦場がそちら |

第三者から見ると、いまの0UTL1ERは**②が自然**。MEO の客と Kubernetes の客は重ならないし、混ぜるとどちらにも「よく分からない会社」に見える。一方で、会社の信用（会社概要・代表・所在地）は両方に共通なので、1つのサイトにまとめておく利点がある。売上の大半が集客支援で、営業もそちらに注力するなら、③も検討する価値がある。

### ②の場合のメニュー（案）

> ※ 実績はサービスページの中に置く方針になったため、最新のメニュー案は [03-services.md](03-services.md) §6。

**グローバルナビ（上部）** — 5項目まで

| 表示名 | 中身 | 理由 |
|---|---|---|
| サービス ▾ | 集客支援 / 受託開発 / プライベートクラウド（/ 派遣） | 見に来た理由の大半。プルダウンで事業を直接選べるようにする |
| 実績・事例 | 全事業の事例一覧 | 「本当にできるのか」に答える場所。A・B とも最も見る |
| 会社情報 | 会社概要・代表メッセージ・メンバー・アクセス | D・E が真っ先に探す |
| お知らせ | お知らせ・コラム | 頻繁に更新できる場合だけ上に置く。更新が少ないならフッターへ |
| **お問い合わせ**（ボタン） | フォーム | 常に右端に目立たせて置く |

- 今の「事業内容」と「サービス」は1つにまとめる（今は中身が重複していて、名前の区別もつかない）
- 「メンバー」は会社情報の中へ。1人だけで独立したメニューにすると、かえって小さく見える
- 料金は独立メニューにせず、各サービスページの中に置く（事業ごとに料金の考え方が違うため）
- 電話番号をナビ右上に置く（A の客は電話で問い合わせることが多い）

**フッター**

```
サービス           会社情報          その他             連絡先
├ 集客支援          ├ 会社概要        ├ お知らせ          ├ 住所
├ 受託開発          ├ 代表メッセージ   ├ 採用情報          ├ 電話・受付時間
├ プライベート      ├ メンバー        ├ プライバシーポリシー├ メール
│  クラウド         └ アクセス        ├ 情報セキュリティ方針└ お問い合わせ
└ (派遣)                              ├ 特商法表記（必要なら）
                                      └ 派遣の情報公開（必要なら）
```

## 5. トップページの構成案

トップの仕事は「全部説明すること」ではなく、**来た人を3秒で正しいページへ振り分けること**と、**信用できる会社だと感じてもらうこと**の2つ。

| 順 | セクション | ここで答えること | 必要なデータ | 現状 |
|---|---|---|---|---|
| 1 | **ファーストビュー** | 何の会社か、誰向けか（1文） | 会社を一言で表す文。スローガンは添える程度 | △（「相関の外側へ」だけでは何の会社か分からない） |
| 2 | **入口の振り分け** | 自分はどこを見ればいいか | 「店舗・地域ビジネスの集客」「企業のシステム開発・インフラ」の2枚のカード | ✕ |
| 3 | **数字で見る実績** | 本当にやっている会社か | 支援店舗数、継続率、開発件数、稼働年数など。**本当の数字だけ** | ✕ |
| 4 | **事例を2〜3件** | うちに近い例はあるか | 事業をまたいで代表的な事例（業種・課題・結果） | ✕ |
| 5 | **選ばれる理由** | 他社と何が違うのか | 社名の由来（相関の外側＝価格と品質の両立）と、それを裏付ける事実（自社でクラウド基盤を運用、AI を開発工程に組み込み等）。言葉だけでなく理由ごとに根拠を1つ添える | △（言葉だけ） |
| 6 | **進め方** | 頼んだらどうなるか | 相談→提案→契約→開始の4段階程度 | ✕ |
| 7 | **代表の顔と言葉** | 誰がやっているのか | 代表の写真、短いメッセージ、経歴 | △（名前のみ） |
| 8 | **お知らせ（最新3件）** | 動いている会社か | 日付つきの記事 | △（1本） |
| 9 | **問い合わせ** | 次に何をすればいいか | フォーム・電話・受付時間。「無料診断」など気軽な入口 | △（フォームは送信不能） |

- 今のトップにある「3つの要素（クラウド/OSS/AI）」は、作り手から見た強みの並べ方。客が知りたい「何を頼めるか」になっていない。§5の「選ばれる理由」の材料として使う
- 散布図の絵は社名の由来を説明する場所（5. 選ばれる理由、または会社情報）に移すと意味が伝わる

## 6. 集めるデータの一覧（優先順）

### 最優先 — 無いと信用を失う・法令に関わる
- [ ] お問い合わせフォームを実際に届くようにする（不具合）
- [ ] プライバシーポリシー
- [ ] 電話番号・受付時間
- [ ] 設立年月日・資本金・従業員数・法人番号
- [ ] 派遣を実施しているか → していれば許可番号と法定の情報公開、していなければ事業から外す
- [ ] ネット上で申し込み・決済を受けるか → 受けるなら特商法表記

### 次点 — 無いと検討の土台に乗らない
- [ ] 事業ごとの「何をするか」（作業の具体的な一覧）
- [ ] 事業ごとの料金の目安・契約期間・解約条件
- [ ] 事例（掲載許可を取ったもの）: 事業ごとに最低1〜2件。業種・課題・やったこと・結果の数字
- [ ] 実績の数字（支援社数・継続率・開発件数など。小さくても本当の数字）
- [ ] 代表の経歴と写真、代表メッセージ

### その次 — あると強くなる
- [ ] クラウドの仕様（データの所在、稼働率、バックアップ、監視、障害時の連絡）と比較表
- [ ] 進め方（相談から開始まで）
- [ ] FAQ（事業ごとに5〜10問、実際に聞かれた質問から）
- [ ] 主要取引先・取引銀行・沿革
- [ ] オフィス・作業風景の実写真（ストック写真の置き換え）
- [ ] 情報セキュリティ方針
- [ ] 採用情報

## 7. 決めてほしいこと

1. **入口の分け方**: ①事業別 / ②客別（推奨） / ③集客支援は別サイト
2. **掲げる事業の範囲**: 派遣・育成は実態があるか。無ければ外すか「準備中」にする
3. **主役の事業**: トップで最初に見せるのは集客支援か、開発・クラウドか
4. **お知らせの更新頻度**: 月1本以上書けるならグローバルナビ、無理ならフッター
