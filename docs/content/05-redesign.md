# 05. HP 再設計案（00〜04 のまとめ）

00〜04 の議論と調査を1枚にまとめた設計案。**メニュー・ページ構成・URL はこの文書を最新とする。**
（01〜03 の中のメニュー案は途中経過）

---

## 1. 設計の前提

1. **客は2種類いる。** 話が通じる言葉がまったく違うので、入口で分ける。
   - A: 店舗・地域ビジネス（MEO・SEO・ホームページ）
   - B: 企業のIT担当（受託開発・プライベートクラウド）
2. **会社の信用は1か所にまとめる。** 会社情報・代表・所在地は A・B 共通なので、サイトは1つ。
3. **実績はサービスの中に置く。** 「このサービスで、こういう結果が出た」の順で読ませる。
4. **読みものはブログ1本にまとめる。** ガイドや用語集の専用コーナーは作らない（04 の調査結果）。
5. **数で稼がず、正直さで差をつける。** 料金を数字で出す、事例に日付と測り方を付ける、比較記事では自社の立場を明かす。MEO 業界では料金を公開しているのが25社中14社、2年以内の実績を出しているのは1社だけなので、これだけで上位に並べる。

## 2. サイトマップ

```
/                                   トップ
│
├─ /services                        サービス一覧（A・B の振り分け）
│   ├─ /services/meo                MEO（Googleマップ集客）            … A
│   ├─ /services/seo                SEO・Webサイト改善                 … A
│   ├─ /services/website            ホームページ制作・移転・保守        … A
│   ├─ /services/development        受託開発                           … B
│   ├─ /services/private-cloud      マネージドプライベートクラウド      … B
│   ├─ (/services/dispatch)         エンジニア派遣・育成 ※実施していれば … B
│   └─ /services/{service}/cases/{slug}   事例の詳細（正本はここ）
│
├─ /cases                           全事例の一覧 ※メニューに出さない（営業でURLを送る用）
│
├─ /blog                            ブログのトップ（入口2つ＋ジャンルのタブ＋新着）
│   ├─ /blog/category/{ジャンル}    ジャンル別ページ（そのジャンルの入口）
│   └─ /blog/{slug}                 記事
│
├─ /company                         会社情報（会社概要・代表メッセージ・社名の由来・沿革・アクセス）
│   └─ /members/{slug}              メンバー紹介
│
├─ /contact                         お問い合わせ（サービスを選んで送れる）
├─ /news                            お知らせ（休業・料金改定など）※フッターのみ
│
└─ 規約・法定表示 ※フッターのみ
    ├─ /privacy                     プライバシーポリシー
    ├─ /security                    情報セキュリティ方針（クラウドを売るなら必要）
    ├─ /legal/tokushoho             特定商取引法に基づく表記（ネットで申込・決済を受けるなら）
    └─ /legal/dispatch              派遣の情報公開（派遣を実施するなら）
```

### 作らないもの
| 作らない | 理由 |
|---|---|
| `/guide`、`/glossary` | 手本の Databricks も用語集をブログへ統合した。用語集は検索からのクリックがほぼ無い。薄いページが増えるとサイト全体の評価が下がる |
| 市町村ごとの地域ページの量産 | Google が「誘導ページ」としてスパム扱いする典型。久喜のページを作るなら、地元の事例がそろってから1枚だけ |
| 独立した「実績」メニュー | 実績はサービスの中に置く方針 |
| 競合名入りの比較ページ（`/vs/〇〇`） | 指名で比較される規模ではなく、自画自賛型はいま最も順位を落としやすい |

## 4. トップページ

トップの仕事は2つ。**来た人を3秒で正しいページへ振り分けること**と、**信用できる会社だと感じてもらうこと**。

| 順 | セクション | 中身 | 必要なデータ |
|---|---|---|---|
| 1 | ファーストビュー | 何の会社かを1文で（例: 「久喜から、お店の集客と企業のシステムを支えます」）。スローガン「相関の外側へ」は添える程度 | 会社を一言で表す文 |
| 2 | **入口2枚** | 「お店・地域の事業者さま」「企業のIT担当者さま」のカード。中にそれぞれのサービス名と、代表的な数字を1つ | サービス一覧 |
| 3 | 数字で見る実績 | 3〜4個。**本当の数字だけ**、時点つき | 支援店舗数、継続期間、運用年数、稼働率など |
| 4 | 事例 2〜3件 | A・B から代表的なもの。カードからサービスページの事例へ | 事例（Strapi） |
| 5 | 選ばれる理由 | 社名の由来（相関の外側＝価格と品質の両立）と、それを裏付ける事実。理由ごとに根拠を1つ。散布図の絵はここで使う | 根拠（自社基盤を自分で運用、料金公開、など） |
| 6 | 進め方 | 相談 → 診断・提案 → 契約 → 開始 → 報告 | 各段階の期間 |
| 7 | 代表の顔と言葉 | 写真、短いメッセージ、プロフィールへのリンク | 代表の写真・経歴 |
| 8 | ブログ新着 | A 向け・B 向けを分けて2〜3本ずつ | ブログ（Strapi） |
| 9 | お問い合わせ | 「無料で相談」ボタン、電話、受付時間 | — |

## 5. サービスページ（全サービス共通の型）

| 順 | セクション | 答えること |
|---|---|---|
| 1 | 冒頭 | 誰の、何を、どうするサービスか。主な成果の数字1つ |
| 2 | こんなお悩みに | 自分ごとか（客の言葉のまま3〜5個） |
| 3 | やること | 具体的な作業。「月に何回」「何を」まで |
| 4 | **実績** | 数字の実績＋事例カード2〜4件。0件ならセクションごと外す |
| 5 | 選ばれる理由 | 理由3つ、それぞれに根拠 |
| 6 | 料金 | プラン表、初期費用、最低契約期間、解約条件、含まれない作業 |
| 7 | 進め方 | 段階と期間 |
| 8 | よくある質問 | 実際に受けた質問 5〜10問 |
| 9 | ほかの会社とくらべる | 比較・選び方のブログ記事へのリンク（書いたら） |
| 10 | 関連する記事 | 対応ジャンルのブログ記事3本 |
| 11 | お問い合わせ | そのサービス専用の入口（例:「無料でマップ診断」）。フォームにサービス名を自動で入れる |

- 料金: A 向け（MEO・SEO・ホームページ）は**数字で出す**。B 向け（開発・クラウド）は「目安」か「ご相談」でよい
- 各サービスで書くべき中身の詳細は 03 §5、原稿のひな形は `services/_template`

## 6. 事例

- 正本は `/services/{service}/cases/{slug}`。複数サービスにまたがる事例も、主なサービスの下に1つだけ置き、他のサービスページからはカードでリンク
- `/cases` は全事例の一覧（サービス・業種・地域で絞り込み）。メニューには出さず、フッターと営業用
- 事例ページの型: 見出しに結果の数字 → 冒頭に「課題／やったこと／結果」の要約 → 業種・地域・期間 → 本文 → お客様の声 → 同じサービスの相談ボタン
- 決まり: 掲載許可を範囲ごと記録する。数字には期間と出典を付ける。「最大〇倍」の切り取り・順位保証・「No.1」は書かない。2年以上前の事例は更新するか外す
- 事例が50件を超えたら、`/cases` を正本に移す構成に切り替えを検討する

## 7. ブログ

### 構成
```
/blog
├─ 入口2つ:「お店の集客の話」「開発・インフラの話」
├─ ジャンルのタブ（集客・MEO / Web・SEO / 開発 / インフラ・クラウド / 会社・考え方）
└─ 新着一覧（タブで絞り込める。最初は全部）

/blog/category/{ジャンル}
├─ そのジャンルの説明 2〜3行
├─ まず読む3本
├─ 一覧
└─ 対応するサービスへの案内
```

| ジャンル | slug | 読者 | つなぐサービス | 配信先 |
|---|---|---|---|---|
| 集客・MEO | `local-marketing` | A | MEO | note |
| Web・SEO | `seo` | A | SEO・ホームページ | note |
| 開発 | `development` | B・採用 | 受託開発 | Zenn |
| インフラ・クラウド | `infrastructure` | B・採用 | プライベートクラウド | Zenn |
| 会社・考え方 | `company` | 全員 | 会社情報 | note |

### 記事の型
| 型 | 中身 | 必須 |
|---|---|---|
| 解説（〇〇とは・やり方） | 定義を最初に1文、目次、手順、よくある失敗、最後に「0UTL1ER でできること」 | 一次情報を1つ（自社の画面・数字・実際に受けた質問） |
| **比較・選び方** | 「安いMEO代行を探してみました」型 | 下の決まりをすべて守る |
| 技術記録 | 環境、起きたこと、原因、直し方 | 自社基盤での実体験 |
| 事例の裏話 | 事例の詳しい経緯 | サービスページの事例へリンク |
| 考え方 | 代表の実体験と判断の理由 | 具体的な場面 |

### 比較・選び方記事の決まり
1. 冒頭に開示文:
   > この記事は、埼玉県久喜市の 0UTL1ER株式会社が書いています。比べている会社の中に、当社の「MEO運用代行」も入っています。他社の料金と内容は、2026年〇月〇日に各社の公式サイトで確かめたものです（当社調べ）。その後に変わっていることがあるので、申し込む前に各社の公式サイトでもご確認ください。当社がいちばん合う、とは限りません。記事の最後に「当社が向かない方」も書いています。
2. 調べ方（何社・いつ・どこから・何の基準で）を書く
3. 料金は同等のプラン同士で比べ、各社の公式URLと確認日を付ける
4. 自社を常に1位にしない。総合順位ではなく「〇〇な人にはこの会社」と用途別に書く
5. 他社が勝つ点と、自社が向かない人を書く
6. 「No.1」「最安」「業界最高」は使わない
7. 四半期に1回、他社の料金を確認し直す。直したら変更履歴に書く
8. note・Zenn には出さない

### 記事ページに必ず付けるもの
書き手（写真・肩書・プロフィールへのリンク）、公開日と更新日（中身を直したときだけ更新）、目次、パンくず、関連記事、ジャンルに合った末尾の案内（ボタンは最後に1つ、多くても冒頭と最後の2つ）、記事ごとの OGP 画像。

### Zenn・note への配信
- 自社ブログに先に出し、Google に登録されたのを確かめてから（3〜7日後）
- 全文転載はしない。読者に合わせて書き直した版に、元記事へのリンクを付ける
- Zenn は技術記録、note は集客・考え方の話。比較記事・事例は配らない
- 社員の個人アカウントで出すなら、冒頭に「筆者は 0UTL1ER の社員です（PR）」

## 10. データの持ち方（Strapi）

> ※ CMS の選定は 06（docs/research/reports/顧客も使うヘッドレスCMSの選定.md）で見直し中（推奨は Payload）。下の型の設計は CMS を問わずそのまま使える。

既存の Strapi（cms.0utl1er.tech）に型を足す。管理画面は Strapi のものを使い、自作しない。

| 型 | 主な項目 |
|---|---|
| Service | 名前、slug、入口（A/B）、料金表、流れ、FAQ、数字の実績 |
| Case | 主なサービス、関連サービス、業種・地域・期間、課題・やったこと・結果（数字＋測り方）、お客様の声、公開の程度、**掲載許可の記録（非公開項目）** |
| Post | 本文、ジャンル、記事の型、書き手、公開日・更新日、次の見直し日、Zenn 版・note 版の本文と URL |
| Category / Author | 説明文、まず読む3本 / メンバーとのつながり |
| News | お知らせ |

- 事例の「公開の程度」は、既存の Contract 型（守秘の設定を親に持たせて配下に効かせる）の作りを手本にする
- 型を作る前に、Strapi のデータベースと画像の置き場所にバックアップがあるか確認する
